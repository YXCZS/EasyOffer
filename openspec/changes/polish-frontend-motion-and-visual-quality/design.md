## Context

当前前端使用 Taro 4.2.1、React 18、TypeScript 和 SCSS。全局样式已经定义基础颜色变量，但主按钮、卡片、标题和状态样式仍分散在各页面中重复实现。现有动画主要集中在题目生成、报告生成和加载转圈，首页、答题反馈、报告呈现、个人中心、知识库及历史记录缺少统一的动效规则。

本设计遵循 `proposal.md` 和 `specs/frontend-motion-and-visual-feedback/spec.md`。微信小程序是主要运行环境，必须控制包体、重排、持续动画数量和基础库兼容风险。

## Goals / Non-Goals

**Goals:**

- 建立可复用的视觉 token 与动效 token，减少跨页面样式漂移。
- 让所有关键交互有一致、即时且不改变布局的反馈。
- 用真实业务状态驱动生成、上传、答题和报告阶段动画。
- 优先打磨首页到报告的核心流程，再覆盖个人中心、知识库和历史记录。
- 保证动画可以被跳过或中断，业务状态始终独立于动画生命周期。

**Non-Goals:**

- 不重做页面信息架构，不改变现有底部 TabBar。
- 不修改后端接口、数据库结构、生成策略、答题持久化或报告规则。
- 不引入大型 UI 框架、动画框架、3D 场景或自定义渲染引擎。
- 不追求游戏化、粒子特效、大面积渐变或每个元素都运动的展示风格。
- 不以动画延长第一题可见时间或报告可见时间。

## Decisions

### 1. 建立全局设计 token，而不是逐页继续追加样式

在全局样式中补充以下类别的变量，并逐步让页面使用这些变量：

- 颜色：品牌、信息、成功、提醒、错误、表面、边界和文字层级。
- 尺寸：字号层级、页面边距、模块间距、控件高度、圆角和阴影。
- 动效：快速反馈、状态切换、内容进入、阶段切换的时长和缓动。

建议基准时长为：按压 `120-160ms`、状态切换 `180-240ms`、内容进入 `280-360ms`、阶段切换 `400-520ms`。循环加载动画独立控制在 `1.6-2.4s`。

备选方案是继续在各页面维护独立样式。该方案改动较快，但会继续产生同名按钮尺寸不同、状态不一致和后续维护成本高的问题，因此不采用。

### 2. 动效以 CSS transform 和 opacity 为主

按钮按压、卡片进入、选项切换、提示出现和模块显隐优先使用 `transform`、`opacity`、颜色和阴影过渡。这些属性在微信小程序中实现成本较低，也较少触发布局重排。

`Taro.createAnimation` 只用于需要由程序明确控制的多阶段序列。`requestAnimationFrame` 仅保留给确实需要逐帧更新的场景；本次不启用 Skyline Worklet，也不新增动画依赖。

备选方案是引入第三方动画库。它会增加包体、组件适配和微信小程序兼容风险，而本项目需要的动效可以由现有能力完成，因此不采用。

### 3. 建立少量公共交互样式和组件

统一以下公共行为：

- 主按钮、次按钮、危险按钮、图标按钮。
- 返回按钮、列表箭头和菜单行。
- 可点击卡片、分段控件、题目选项。
- 加载、成功、错误、空状态和进度条。

公共实现只负责外观和交互反馈，不封装业务请求或页面导航。现有页面可以逐步迁移，避免一次性重写所有 JSX。

### 4. 使用“答题节奏线”统一核心流程

新增轻量进度视觉组件或公共样式，将相同视觉语言复用于：

1. 题目生成页的真实阶段节点。
2. 答题页的当前题号和可用题目进度。
3. 报告生成页的分析阶段。
4. 报告页的完成收束状态。

组件只消费页面已有状态，不自行计时推断完成。第一题可用时立即导航，完成动画不得阻塞跳转。

备选方案是每个页面设计独立加载动画。视觉表现会更丰富，但用户无法形成统一的阶段认知，也会增加维护成本，因此不采用。

### 5. 页面动画采用“一次编排”，避免散点动画

每个页面最多设置一个主要进入序列：

- 首页：标题、核心输入区和主操作形成一个短序列；未完成练习只在首次加载时轻量进入。
- 答题页：题目切换使用方向过渡；提交后先展示结果，再展开解析和配图。
- 报告页：首屏分数、统计和知识点进度进入；长列表不做逐项延迟。
- 个人中心、知识库、历史记录：只保留控件反馈和关键状态切换。

页面从后台恢复或 TabBar 切回时不重复播放完整开场动画，避免频繁打断操作。

### 6. 动画状态与业务状态分离

业务 store 和接口响应继续作为唯一数据来源。页面可以增加短生命周期的展示状态，例如进入方向、反馈可见性和阶段变化标识，但不能复制或覆盖题目进度、用户资料、上传状态等业务数据。

异步任务必须以现有版本号或最新状态为准，旧响应不能触发阶段回退。动画结束回调仅用于清理展示类名，不用于提交答案、保存进度或发起导航。

### 7. 提供弱动效与中断策略

对支持 `prefers-reduced-motion` 的目标使用媒体查询关闭位移和循环动画；同时保证所有状态在没有动画时直接显示最终结果。微信环境下即使无法读取系统偏好，也通过短时长、低频循环和限制并行动画数量降低风险。

页面隐藏、卸载或快速切换时不等待动画完成。所有定时器、轮询和展示状态按现有生命周期清理。

### 8. 视觉优化以现有配色为基础

保留蓝色品牌主色，并使用紫色表示生成或思考、绿色表示正确或完成、橙色表示待巩固、红色表示错误。减少单一蓝色在大面积页面中的占比，但不改成高饱和多彩主题。

中文字体继续使用系统字体栈，数字使用等宽数字特性，避免下载字体造成包体和首屏闪烁。图标保持统一线宽和触控尺寸，优先复用本地资源或小程序兼容实现。

## Risks / Trade-offs

- [Risk] 大量页面同时调整可能造成样式回归 -> 按核心流程、扩展页面分批迁移，每批都进行截图与交互回归。
- [Risk] 动画类名和页面状态交织后导致重复播放 -> 动画状态只存在页面展示层，并对首次进入、TabBar 恢复和异步更新分别定义触发条件。
- [Risk] 题目切换动画影响已选答案 -> 渲染切换与 session 数据解耦，动画期间保留当前题目快照，完成后再清理展示状态。
- [Risk] 持续动画造成低端设备卡顿 -> 限制同时运行的循环动画数量，优先 transform/opacity，并提供弱动效规则。
- [Risk] 公共样式覆盖页面现有选择器 -> 分阶段迁移，避免高权重类型选择器，迁移完成后再删除重复定义。
- [Trade-off] 不引入专业动画库会减少复杂弹簧和形变效果，但能显著降低包体与兼容风险，更符合面试工具的克制定位。

## Migration Plan

1. 建立全局 token、公共交互状态和弱动效规则，不删除现有页面样式。
2. 迁移公共返回按钮、主次按钮、图标按钮和卡片按压反馈。
3. 改造首页、题目生成、答题、报告生成和报告页面，并完成核心流程验证。
4. 改造个人中心、知识库、历史记录和历史详情页面。
5. 删除确认不再使用的重复样式，执行类型检查和微信小程序生产构建。
6. 在微信开发者工具中按登录/游客、生成成功/失败、答题前进/后退、报告、上传、重命名和退出登录场景进行截图与手动验证。

回滚时可以按页面撤销新类名和公共样式引用；本次没有数据库和后端迁移，不涉及数据回滚。

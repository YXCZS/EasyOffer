## Context

现有 `/quiz/generate` 在一个请求内调用 DeepSeek 并等待六道题全部返回，`Quiz` 模型也要求题目数量固定为六道。答题页和进度保存目前围绕完整 Quiz 工作，因此增量实现需要引入“生成任务/题目草稿”边界，不能把不完整题组直接伪装成完整历史记录。详见 proposal.md 的 Why；本设计对应 specs/incremental-quiz-generation/spec.md 的行为约束。

## Goals / Non-Goals

**Goals:**

- 用轮询实现首题优先，用户拿到第一道通过校验的题后即可进入答题页。
- 后台继续生成剩余题目，生成结果可原子查询、可恢复，并在答题期间保存答案。
- 一次任务只做一次证据准备和路由判断，后续题目复用同一 ResearchContext，避免每道题重复调用 Tavily/Chroma。
- 任务完成后复用现有完整 Quiz、quiz_sessions、progress、report 和历史记录流程。
- 保持现有同步接口、匿名用户生成能力和底部导航兼容。

**Non-Goals:**

- 本次不引入 SSE、WebSocket、消息队列、Celery 或新的外部任务服务。
- 不改变题目数量、题型、报告算法、XP 规则或知识库内容处理流程。
- 不将低质量或未校验的题目推送给前端，也不允许用部分题目生成最终报告。

## Decisions

### 1. 采用轮询任务模型，不采用 SSE

新增任务创建和状态查询接口，前端以约 800-1000ms 的间隔轮询；页面隐藏时停止轮询，重新显示时立即查询。微信小程序对长连接、后台切换和网络重连的处理成本较高，轮询更容易复用现有 `Taro.request`、调试工具和错误处理。状态接口返回版本号，客户端只在版本变化时合并题目，避免重复渲染。

备选方案是 SSE：实时性略好，但需要处理小程序网络请求兼容、连接断开、代理缓冲和服务端连接生命周期，当前 MVP 的收益不足以抵消复杂度。

### 2. 新增生成任务表，完整题组完成后再落入现有题目会话

新增 `quiz_generation_tasks` 表保存 `task_id`、可选 `user_id`、请求参数、任务状态、版本、已生成题目 JSON、答案 JSON、题目元数据、错误信息、创建/更新时间和过期时间。已登录用户查询时按 user_id 校验归属；匿名任务使用高熵 task_id 作为短期访问凭据，并设置较短 TTL。

任务状态使用 `queued`、`generating`、`completed`、`failed`、`expired`。每次题目生成成功在同一事务中写入题目、generated_count 和 version。全部六道题通过最终校验后，才调用现有保存逻辑创建 quiz_sessions/progress；重复完成请求使用 task_id/quiz_id 幂等约束，不能创建重复记录。

### 3. 将单题生成封装在现有 DeepSeek 生成器内部

保留现有 `generate(request)` 作为同步兼容入口，新增内部的单题生成能力：任务开始时执行一次主题判断、文档校验和 Agentic RAG 证据准备；每轮只请求一道题，并传入题目序号、已有题干摘要和共享证据上下文以约束唯一性。单题结果使用与现有 Question 相同的结构校验；全部题目完成后再构造完整 Quiz，补齐标题、摘要、模型版本、来源和 evidence_meta。

逐题调用会增加总模型调用次数，因此设置每题最大重试次数、任务总超时和上下文长度上限；证据只准备一次，避免 Tavily/Chroma 成本按题目倍增。旧同步入口继续走现有一次性生成逻辑，作为灰度和回滚路径。

### 4. 以任务草稿承载前端部分题目，以完整 Quiz 兼容现有答题能力

前端会话增加可选的 `generationTaskId` 和增量题目状态，草稿只包含已生成的 Question 和必要元数据。生成页在第一次轮询得到至少一道题后跳转答题页；答题页按当前索引读取已生成题目，如果下一题尚未到达则显示等待状态并继续轮询。答案先通过任务进度接口保存，任务完成后切换到现有 quiz progress 接口；完整 Quiz 到达后，报告入口保持不变。

这样避免修改后端 `Quiz.questions` 的六题约束，也避免把部分题目写入历史记录。旧的本地 session 数据缺少 generationTaskId 时按普通完整练习恢复。

### 5. 接口和后台执行边界

- `POST /api/v1/quiz/generation-tasks`：创建任务，返回 task_id、状态、计数和已生成题目。
- `GET /api/v1/quiz/generation-tasks/{task_id}`：返回原子状态快照。
- `PUT /api/v1/quiz/generation-tasks/{task_id}/progress`：保存任务未完成期间的当前索引和答案，使用 version 做乐观并发控制。
- `POST /api/v1/quiz/generation-tasks/{task_id}/retry`：仅对失败任务创建受控重试，复用已生成题目并从失败题序继续，避免重复生成已成功题目。

FastAPI `BackgroundTasks` 承载单实例 MVP 的后台循环；应用启动时把遗留的 generating 任务标记为 failed/recoverable，避免永久卡住。任务状态查询不直接暴露其他用户数据，所有数据库异常和模型异常沿用现有 API 错误结构并写入日志。

### 6. 前端轮询与用户体验

生成页保留当前生成动画和失败状态，新增“已准备 X/6 道题”的进度信息。首题到达立即进入答题页，不再等待全部题目；答题页底部按钮在下一题未准备好时变为禁用的等待状态，收到新题后自动恢复。轮询失败采用有限重试和退避，任务失败显示已生成数量、错误原因和“继续重试/返回首页”入口。

## Risks / Trade-offs

- [六次单题调用可能提高总成本和总完成时间] → 证据只检索一次，限制每题重试和上下文长度；保留同步接口及灰度开关。
- [进程重启会中断 BackgroundTasks] → 启动时恢复为可重试状态；任务表保留已生成题目，不重复生成已完成题目。
- [网络轮询造成请求数量增加] → 使用版本号、800-1000ms 初始间隔、页面隐藏暂停和最大退避；任务完成或失败立即停止。
- [部分题目与答案持久化边界复杂] → 未完成数据只写生成任务，完整题组完成后一次性写入 quiz_sessions/progress；报告接口拒绝 incomplete 任务。
- [并发轮询或重复重试导致重复题目] → 任务行锁/乐观版本号、题目 ID 和题干唯一性校验，并以 task_id 做幂等完成。
- [匿名任务可被猜测] → 使用高熵随机 task_id、短 TTL 和最小返回字段；用户登录后任务绑定 user_id，跨用户访问统一返回资源不存在。

## Migration Plan

1. 新增任务表和后端任务模型/接口，先不改变现有 `/quiz/generate`。
2. 增加单题生成器、任务循环、状态快照和任务进度保存测试。
3. 前端增加增量 API 与 session 字段，在灰度开关开启时使用首题优先流程。
4. 验证普通主题、知识库专属主题、Tavily 失败降级、首题失败、后续题失败、离开恢复和报告生成。
5. 默认开启增量流程；若错误率、成本或资源占用异常，关闭开关后回退同步接口。任务表数据可按 TTL 清理，不影响现有 quiz_sessions。

## Open Questions

无。题目数量沿用现有固定六题，轮询间隔、单题超时和任务 TTL 属于实现阶段可通过测试校准的运行参数，不改变本规格行为。

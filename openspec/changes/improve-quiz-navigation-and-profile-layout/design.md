## Context

当前答题页使用 Zustand 会话中的 `currentIndex` 同时决定页面显示题目和服务端断点位置，`advanceQuestion` 会向后端保存新索引，增量出题快照也会合并该索引。若“上一题”直接递减 `currentIndex`，将可能把未完成练习的恢复点倒退、与后台轮询互相覆盖，或触发现有进度版本冲突。

答题页目前只有一个全宽底部主按钮；答题页的图标加文字胶囊返回控件与报告页的图标按钮在位置和尺寸上不同。个人页的昵称修改入口位于用户信息区外，并通过负外边距独立右对齐；退出登录区域下方还有一个与底部 Tab 重复的“返回答题”按钮。

本设计只调整 Taro 前端状态和布局。后端接口、数据库、生成任务、报告生成和用户资料协议均保持不变。需求行为以本 change 的三个 delta spec 为准。

## Goals / Non-Goals

**Goals:**

- 在不倒退持久化断点的前提下支持上一题回看和逐题向前返回。
- 让增量生成轮询与历史题回看同时工作，新增题目不打断用户当前视图。
- 建立二级页面返回控件和答题底部操作区的轻量统一规范。
- 将昵称编辑整合到用户信息区，并移除重复的“返回答题”按钮。

**Non-Goals:**

- 不允许修改已经提交的历史答案，也不重新判题。
- 不改变题目生成、答案保存、未完成练习、报告或登录接口。
- 不修改底部 Tab 配置，不对全部页面进行视觉重构。
- 不新增 UI 框架、图标库、数据库迁移或后端代码。

## Decisions

### 1. 使用页面级 `viewIndex` 表示正在浏览的题目

答题页新增本地浏览索引 `viewIndex`，并以会话中的 `currentIndex` 作为“最远到达位置”。首次进入或恢复练习时，`viewIndex` 初始化为合法范围内的 `currentIndex`。渲染题目、题号和按钮状态使用 `viewIndex`；服务端自动保存和恢复继续使用会话中的最远位置。

点击“上一题”只递减 `viewIndex`。用户在历史题目点击“下一题”时只递增 `viewIndex`，直到回到最远位置；只有在最远位置提交新答案或向首次到达的新题前进时，才调用现有的 `recordAnswer`、`advanceQuestion` 和进度保存逻辑。

选择该方案是因为它不会改变现有 Zustand/后端进度协议。备选方案是直接递减 `currentIndex`，但会使断点续答倒退，并可能与增量快照的 `Math.max` 合并规则产生界面跳动，因此不采用。

### 2. 历史题目从 `answerRecords` 恢复为只读状态

当 `viewIndex` 指向最远位置之前的题目时，通过题目 ID 查找已有答题记录，恢复用户选择、正误结果、正确答案和解析。历史题的选项禁用，底部右侧操作固定承担“下一题”浏览职责，不触发再次提交。

选择只读回看是为了保持一题一次判定和报告数据一致。允许改答案会要求重新定义得分、XP、报告和服务端版本语义，超出本次范围。

### 3. 增量轮询只扩充题目，不覆盖回看位置

轮询仍将生成快照合并到 Zustand 会话，`currentIndex` 继续采取不倒退规则。本地 `viewIndex` 不随新题数量或生成快照自动跳转；只在当前索引超出有效题目范围等异常情况下进行边界修正。用户在生成前沿等待时，沿用现有等待页面和轮询节奏，新题可用后恢复正常答题。

该决策避免“回看上一题时突然被新题拉走”。备选方案是每次快照后同步 `viewIndex = currentIndex`，但它会破坏用户正在进行的回看，因此不采用。

### 4. 答题底部采用固定双操作布局

底部操作区改为稳定的两列布局：左侧为次要样式的“上一题”，右侧为主操作。两者高度、圆角、垂直对齐和按下反馈一致；左侧宽度固定且足够容纳中文标签，右侧占剩余空间，以兼容“提交答案”“下一题”“查看本轮报告”等长度。第一题保留左侧占位但禁用，避免主按钮随题号横向跳动。

操作区继续处理底部安全区，并为题目正文预留等于操作区高度的底部空间。相比将上一题放在题目顶部，该方案更符合连续作答的拇指操作路径，也不会和页面返回键混淆。

### 5. 用轻量共享返回控件统一二级页面

抽取一个无业务导航假设的轻量返回控件，或在现有公共样式层建立同一套尺寸变量。组件负责安全区偏移、图标、最小 44px 等效触控区域、形状和反馈；各页面继续传入自己的点击行为，例如保存后退出、返回上一页或回到指定入口。

只替换已有自定义返回控件的二级页面，不给“答题”和“我的”根 Tab 页面增加返回键。这样能够统一视觉和触控体验，又不强行改变各页面导航语义。备选方案是只复制 SCSS 数值，但后续容易再次漂移，因此优先共享组件；若现有编译约束不适合抽组件，则至少使用同一公共 mixin/token。

### 6. 昵称入口内联到用户信息区

在头像右侧的用户介绍区内建立昵称行：昵称为主文本，旁边放置紧凑的编辑图标与“修改”标签；XP 保持在信息区右侧或既有位置。进入编辑态后，同一昵称行替换为输入框，并显示保存、取消操作，不再保留独立的 `.profile-edit` 行和负外边距。

长昵称使用可收缩文本区域与必要的截断/换行约束，编辑按钮维持稳定触控区，XP 不参与昵称行宽度争抢。该布局直接表达“修改”作用于昵称，比将按钮放在卡片右下方更清晰。

### 7. 删除重复入口但保留导航能力

从个人页 DOM 中删除退出登录按钮下方的 `back-link`，同时移除仅供它使用的样式。用户仍可通过底部“答题”Tab 回到答题首页；退出登录、登录态清理和其他菜单项逻辑均不改动。

## Risks / Trade-offs

- [本地 `viewIndex` 与异步会话更新不同步] → 所有索引更新按题目 ID 和有效长度校正，并对恢复、追加题目、退出再进入建立前端测试。
- [历史答题记录缺失导致只读页面信息不完整] → 仅对已有记录启用完整反馈；若遇到旧数据缺记录，则安全显示题干并禁用重复提交，同时允许前进回到最远位置。
- [统一返回控件改变个别页面原有导航语义] → 共享组件只统一外观与触控，不内置 `navigateBack`，逐页保留原点击处理函数。
- [双按钮压缩长主操作标签] → 左列使用稳定的紧凑宽度，右列弹性占位，并在小屏微信设备上验证文字不截断、不换行溢出。
- [个人信息区在长昵称下拥挤] → 昵称文本允许收缩，编辑入口固定触控区，并针对 320px 等效窄屏和最大昵称长度进行截图检查。

## Migration Plan

1. 先引入页面级浏览索引和回看渲染逻辑，使用现有会话数据完成单元/交互验证。
2. 更新答题底部操作区和共享返回控件，逐页接入但保留每页原导航回调。
3. 调整个人页昵称编辑布局，删除 `back-link` 节点和专用样式。
4. 执行 TypeScript 类型检查、微信小程序构建，并在微信开发者工具验证正常答题、回看、增量出题、断点恢复、报告、昵称、头像、退出登录和 Tab 切换。
5. 若发现导航或进度回归，可分别回退共享控件接入和 `viewIndex` UI 改动；由于无后端及数据迁移，回滚不需要数据处理。

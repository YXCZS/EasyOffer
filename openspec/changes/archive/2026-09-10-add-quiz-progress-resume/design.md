## Context

现有 `quiz_sessions` 保存题组快照，`answer_records` 和 `reports` 主要在报告生成时写入；前端 `session.ts` 只有一条会话且答题页返回会调用 `reset()`。本变更需要跨越数据库、FastAPI 路由、报告事务和 Taro 页面，因此采用独立进度层，避免改变已有历史表语义。具体行为以 `specs/quiz-progress-resume/spec.md` 为准。

## Goals / Non-Goals

**Goals:**

- 登录用户的进度可在服务端保存并按账号恢复。
- 当前设备的本地状态在服务端暂时不可用时仍可保留。
- 支持多组未完成练习、报告失败重试和完成后进入历史。
- 不改变现有题目生成、逐题判题和报告 API 的主要请求响应结构。

**Non-Goals:**

- 不实现实时多设备协同编辑。
- 不保存未提交的临时选项。
- 不增加新题型、题目编辑、提醒推送或排行榜。
- 不在本变更中重做登录、头像和 XP 体系。

## Decisions

### 1. 使用独立 `quiz_progress` 表

在现有 `quiz_sessions` 旁增加 `quiz_progress`，保存活动状态和增量答案；完成报告继续写入 `answer_records`、`reports`。这样历史查询不会把半完成练习误认为已完成，也能明确表达报告失败状态。

替代方案是直接给 `quiz_sessions` 增加状态和答案字段，改动较少但会混合题组快照和用户进度，后续多用户、版本和历史查询更容易产生歧义，因此不采用。

### 2. 本地立即写入，服务端增量同步

每次提交答案先写 Zustand 和 Taro Storage，再同步服务端；点击返回时等待一次关键同步。这样可以覆盖页面切换和小程序被回收场景，同时不会因为一次网络抖动丢失本地进度。

### 3. 使用版本号乐观锁

每条进度记录维护 `version`。更新请求必须携带客户端版本，数据库使用条件更新；冲突时返回 409 和服务端最新数据。相比悲观锁，乐观锁更适合移动端低频提交，且能防止多设备旧数据覆盖新答案。

### 4. 报告完成使用事务和已有报告幂等判断

报告生成成功后，在事务内写答题记录、报告、完成状态并结算 XP；已有报告时直接返回已有结果。报告生成本身不放在数据库事务中，避免长时间持有锁；只有最终写入阶段使用行锁。

### 5. 接口放在现有用户路由下

新增 `GET /api/v1/user/quizzes/incomplete`、`GET /api/v1/user/quizzes/{quiz_id}/progress` 和 `PUT /api/v1/user/quizzes/{quiz_id}/progress`，复用现有 JWT 和用户 repository 组织方式。静态 `incomplete` 路由必须在动态 `quiz_id` 路由之前注册。

### 6. 前端从单会话迁移到按 `quiz_id` 索引

使用 `practices: Record<string, PracticeSession>` 管理多组练习，并将旧 `easyoffer-session-v1` 一次性迁移到 v2。答题页、报告生成页和首页都以 `quiz_id` 作为显式上下文，避免全局单例会话互相覆盖。

## Risks / Trade-offs

- [网络中断] 服务端保存可能失败 → 本地先写入，保留未同步标记，首页和下次提交时重试。
- [多设备冲突] 两台设备同时提交 → 使用版本号拒绝旧版本覆盖，并让用户重新加载服务端最新状态。
- [历史兼容] 旧题组没有 `quiz_progress` → 报告接口保留旧数据兼容分支，历史列表以已有报告为准。
- [本地数据膨胀] 多组题目完整缓存会增加 Storage 使用量 → 首版限制本地活动练习数量和单题组大小，异常时提示清理已放弃练习。
- [页面快速重复点击] 可能触发重复跳转或请求 → 提交、返回和恢复按钮增加进行中锁，并由后端幂等兜底。

## Migration Plan

1. 执行幂等 SQL，创建 `quiz_progress` 表和索引，不修改或删除旧表。
2. 发布后端模型、repository、进度接口和报告事务改造。
3. 发布前端 session v2；首次启动自动迁移本地 v1 数据。
4. 开启首页未完成模块，观察进度保存失败率和 409 冲突率。
5. 出现问题时关闭首页模块开关，保留本地进度和旧报告接口；修复后重新开启。

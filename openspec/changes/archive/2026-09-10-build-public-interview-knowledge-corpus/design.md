## Context

参见 [proposal.md](./proposal.md) 的动机。当前项目已经实现公共/个人 Milvus 集合、Embedding、公共分块写入、发布状态过滤和 Agentic RAG 路由，但公共集合实际为空；`知识库/` 中的 20 份 PDF 尚未经过批量处理。现有 `split_text` 使用 `RecursiveCharacterTextSplitter(900/120)`，适合作为无结构文本兜底，不足以保证完整面试问答不被割裂。

约束如下：

- 公共和个人知识向量继续存储在 Milvus；MySQL 业务表不因本变更新增公共知识库表。
- COS 继续只承担头像和题目图片，不用于保存知识库正文、向量或原始资料。
- 资料摄取是离线管理流程，不进入用户生成题目的请求链路，也不新增小程序页面。
- 已有 Agentic RAG、Tavily 降级、个人知识库专属模式和增量出题契约保持不变。
- 第三方资料必须先确认许可；未确认许可的数据只能进入本地评估集合。

## Goals / Non-Goals

**Goals:**

- 将现有资料可靠转换为面向技术面试检索的父子知识单元。
- 提供幂等、可预览、可审核、可发布、可撤回的批量内容管线。
- 用可量化的检索基准决定某一知识库版本能否发布。
- 先通过 Redis、MySQL、RAG/Milvus 试点校准，再扩展到其余方向。

**Non-Goals:**

- 不重新设计 Agentic RAG 路由或更换 Milvus。
- 不把公共资料、审核记录迁入现有 MySQL 业务表。
- 不在本阶段建设在线运营后台；管理入口先采用 CLI 和版本化清单。
- 不处理视频、音频和需要 OCR 的扫描版 PDF；扫描文件应进入失败报告，后续单独增加 OCR 能力。
- 不自动抓取并发布互联网内容；网页资料仍须经过来源登记和审核。
- 不承诺一次覆盖所有岗位，首批只对试点领域设置发布质量门槛。

## Decisions

### 1. 使用离线分阶段管线，而不是上传后直接写入公共集合

流程固定为：

```text
资料清单
→ 解析
→ 规范化清洗
→ 结构识别
→ 父子切分
→ 文档/分块去重
→ 元数据补全
→ Embedding
→ 写入候选版本
→ 自动质量检查
→ 检索基准评估
→ 人工抽检
→ 发布或拒绝
```

每个阶段输出结构化 JSONL/JSON 报告并可从上一个成功阶段恢复。运行时 Tavily 结果不自动进入公共知识库。

**原因：** 内容错误和版权问题不能依靠向量检索阶段补救；候选数据必须与生产可检索数据隔离。

**备选方案：** 导入后直接标记 `published`。实现简单，但无法在不污染线上结果的情况下做评估，因此不采用。

### 2. 使用版本化清单和文件报告管理公共语料，不新增 MySQL 表

新增公共资料清单，建议采用 YAML；每条记录包含 `document_id`、路径/URL、来源名、技术、岗位、版本、语言、许可状态和内容类型。每次摄取生成带批次 ID 的 manifest、处理报告和评估报告，保存在运维数据目录并可纳入版本控制；完整第三方正文和密钥不得写入报告。

Milvus 分块保存运行时检索所需元数据。正式发布以 `corpus_version + document_version + status` 过滤；清单和报告是内容治理事实源，Milvus 是检索事实源。

**原因：** 用户已经明确不扩展 MySQL 和 COS 用途；公共内容更新频率低，先使用 CLI 与版本文件能够降低复杂度，同时保留审计能力。

**备选方案：** 新建公共知识库 MySQL 管理表和后台页面。长期更适合多人运营，但超出当前作品集和单人维护阶段。

### 3. 采用“结构优先、父子分块、递归兜底”

解析后先形成带页码和章节路径的块，再按以下优先级识别父知识单元：

1. 明确的“问题/答案/解析”组合；
2. 编号问题及其后续答案段落；
3. 章节标题及其正文；
4. 普通段落集合。

结构识别优先使用确定性规则：编号、问号、标题层级、`答案/解析/总结` 标记、列表和代码围栏。对无法确定边界的内容，可调用 DeepSeek 只返回边界与类型标签，不允许改写正文；模型输出校验失败时回退确定性结果。

父单元建议控制在约 600～1800 个中文字符；父单元过长时使用 `RecursiveCharacterTextSplitter` 生成约 600～900 字符的子块，重叠约 80～120 字符，并启用起始位置记录。参数按内容类型配置，不能散落为硬编码。

检索向量文本由技术标签、问题或章节标题、章节路径和子块正文组合；返回给生成模型的证据仍保留原始正文和来源。命中子块后，通过 `parent_id/document_id/version` 的精确标量查询扩展上下文，而不是使用文件名再次做向量搜索。

**原因：** LangChain 官方仍推荐递归切分作为通用文本切分器，并支持保留起始位置和元数据；但面试资料具有明显问答边界，先保留语义单元可以提高答案完整性。

**备选方案：** 固定 900/120 全量切分。成本最低，但容易把问题、答案和边界条件拆开。

### 4. 使用稳定标识和两级去重保证幂等

- 文档内容哈希：清洗后完整正文的 SHA-256。
- 父单元哈希：规范化问题/标题与正文的 SHA-256。
- 子分块 ID：`document_id + document_version + parent_index + child_index + content_hash` 的稳定摘要。
- 文档级去重先识别完全相同资料；分块级去重再识别转载、重复题解和页眉页脚残留。
- 近重复检测首期采用规范化文本指纹与 token shingles/SimHash，不再调用 Embedding 做全库两两比较。

同一版本重跑使用稳定主键 upsert。Milvus 官方支持在 `auto_id=false` 时用确定性主键 upsert 替换实体。发布新版本前按文档/版本精确删除或失活旧候选分块，避免重复追加。

### 5. 采用候选版本与两阶段发布

所有新分块先写入 `status=unpublished` 的候选版本。完成结构检查、Embedding 数量校验、检索评估和人工批准后：

1. 将候选版本标记为可发布；
2. 切换该文档的活动版本；
3. 将旧版本标记为 inactive/unpublished；
4. 运行发布后冒烟查询；
5. 冒烟失败则恢复旧版本过滤状态。

Milvus 不提供跨实体业务事务，因此发布采用状态过滤和补偿回滚，而不是假定原子多行事务。

### 6. 元数据模型以检索过滤和追溯为中心

每个子分块至少包含：

```text
chunk_id, document_id, document_version, corpus_version,
parent_id, parent_type, child_index, start_index,
technology, role_tags, knowledge_type, section_path,
source_name, source_url, page_start, page_end,
language, content_hash, license_status,
review_status, status, published_at
```

使用现有 Milvus dynamic fields 保存扩展元数据，保留 `status`、`role_tags` 等现有过滤字段兼容性。公共检索继续强制 `published` 和岗位过滤。

### 7. 用黄金查询集和排名指标控制发布质量

首批为 Redis、MySQL、RAG/Milvus 建立 30～50 条查询，覆盖：定义、原理、对比、故障场景、版本差异、口语化表达和组合问题。每条查询保存人工标注的相关父单元以及 0/1/2 相关性等级。

自动评估包括：

- Hit@5：Top-5 是否至少命中一个相关父单元；
- MRR@5：首个相关结果排名；
- NDCG@5：多级相关性排序质量；
- 核心知识点覆盖率；
- 重复结果率和岗位污染率；
- 父上下文恢复成功率和来源可追溯率；
- Milvus 检索 P50/P95 延迟。

试点默认门槛建议：Hit@5 ≥ 0.85、MRR@5 ≥ 0.70、NDCG@5 ≥ 0.75、岗位污染率 ≤ 5%、重复结果率 ≤ 10%、父上下文恢复率和来源可追溯率均为 100%。这些阈值存入版本化配置，可在首轮真实评估后调整，但调整必须记录原因。

人工抽检覆盖高分、低分、冲突和边界样本，判断技术正确性、面试价值、版本适用性和来源质量。自动指标或强制人工项失败时，不得切换生产版本。

### 8. 分阶段导入现有资料

第一阶段只选择 Redis、MySQL，以及新增的 RAG/Milvus 官方资料作为试点。原因是三类资料既包含传统问答结构，又能覆盖新技术和官方文档型内容，适合验证切分策略。

试点达到门槛后，再按以下顺序处理：

1. Java 基础、集合、并发、JVM；
2. Spring、Spring Boot、Spring Cloud、MyBatis；
3. 计算机网络、操作系统、设计模式；
4. Elasticsearch、消息队列、RabbitMQ、Nginx、ZooKeeper；
5. AI 大模型及后续其他岗位资料。

第三方 PDF 在许可确认前只进入本地候选版本。RAG/Milvus、LangChain 等快速变化内容优先使用官方文档并明确版本。

### 9. 与现有 Agentic RAG 的集成边界

本变更不改变路由图。发布完成后，普通登录用户的 `public_milvus_search` 自动检索新内容；证据不足时仍按现有逻辑调用 Tavily 或基础模型。个人知识库模式继续只允许个人 Milvus 与基础模型，游客继续只使用基础模型。

题目生成验证需要额外检查：题干、答案和解析能够对应被召回的父知识单元，且同一套题不会因为重复分块生成高度重复题目。

## Risks / Trade-offs

- **[Risk] PDF 排版导致问题与答案边界误判** → 保存结构置信度，低置信度进入人工抽检；试点失败样本用于补规则，不允许直接发布。
- **[Risk] 第三方资料存在版权或再分发限制** → 清单必须记录许可状态；未确认内容只用于本地评估，生产优先发布官方或明确授权来源。
- **[Risk] 父子扩展增加一次 Milvus 查询和延迟** → 只对被选中的少量 Top-K 父级批量精确查询，并在评估中记录 P95。
- **[Risk] 动态字段过多导致过滤或兼容问题** → 保持核心过滤字段命名稳定，新增字段均有默认值，并在空集合上验证 schema 与查询表达式。
- **[Risk] LLM 边界识别引入非确定性与成本** → 仅处理规则低置信度文本，只允许输出边界和标签；缓存输入哈希结果并提供完全禁用开关。
- **[Risk] 检索指标好但出题质量仍差** → 除离线召回评估外，增加证据到题目的人工一致性抽检和端到端题目唯一性测试。
- **[Risk] 本地 Milvus Lite 与生产 Standalone 表现不同** → 功能测试可使用 Lite，发布前性能和过滤回归必须在目标 Standalone 环境执行。

## Migration Plan

1. 新增清单、候选数据目录和 CLI，但保持公共集合为空或继续使用现有已发布数据。
2. 用小型测试夹具验证解析、结构切分、幂等、版本替换和撤回。
3. 在独立候选 `corpus_version` 中导入 Redis、MySQL、RAG/Milvus 试点资料。
4. 建立黄金查询集并运行自动评估与人工抽检；未达标则只调整候选数据和参数。
5. 通过门禁后发布试点版本，并对 Agentic RAG 进行真实主题冒烟测试。
6. 分批导入剩余资料，每批执行相同回归门禁，避免一次性污染全部领域。
7. 在 Milvus Standalone 上复跑过滤、父级扩展、延迟和端到端出题测试后再作为云端默认知识库。

回滚时将活动 `corpus_version` 切回上一版本并撤销候选版本的 `published` 状态；不删除上一版本分块，不修改 MySQL、COS、个人知识库和答题记录。

- RAG/Milvus 首批官方资料的具体 URL 和版本在实施时写入清单，不影响本设计的管线和验收标准。

## Context

当前项目已经有 FastAPI 生成任务、MySQL 任务快照、DeepSeek 单题调用和 Taro 前端轮询基础，但现有流程仍把六题规划作为出题前置依赖。新的设计将生成任务定义为“有序题目生产队列”：创建接口只负责落库并立即返回任务 ID，资料准备和题目逐题生产在后台执行，题目落库即对客户端可见。微信小程序环境优先使用 HTTP 轮询任务快照实现增量获取，不引入 SSE 长连接。

## Goals / Non-Goals

**Goals:**

- 删除六题蓝图等待环节，让异步任务创建成为即时操作，第 1 题成为唯一首屏等待门槛。
- 后端逐题调用 DeepSeek，题目通过校验后立即写入任务快照。
- 用户答题与后台出题并行，任务快照、题目列表和答题进度保持一致。
- 保留 Chroma、Tavily Search/Extract、Agentic RAG 和基础模型降级能力。
- 让单题失败可重试，部分任务可恢复，终态任务可停止轮询。

**Non-Goals:**

- 不引入 SSE、WebSocket、消息队列或新的后台任务框架。
- 不改变六道题的产品总量、题目数据结构、报告生成和底部导航。
- 不在本变更中调整 RAG 路由算法或知识库切分策略。

## Decisions

### 1. 使用任务快照轮询表达增量推送

后端每次追加题目后更新 MySQL 任务快照，前端使用单飞请求的自适应轮询获取新增题目。微信小程序对 SSE 的连接、生命周期和代理配置支持不稳定，轮询更容易在开发者工具和真机上保持一致；对用户而言，题目写入快照后下一次轮询即可见。轮询基准间隔设为 6 秒，后端响应慢、网络异常或重试场景退避为 8 秒，任务进入终态后立即停止。

### 2. 资料准备与单题生成解耦

主题判断、Chroma 检索和 Tavily 调用只在任务开始阶段执行一次，生成的证据上下文复用于每道题。删除“等待完整六题蓝图”的依赖，单题 Prompt 使用题号、已生成题目摘要和主题资料约束多样性。

### 3. 每题采用乐观版本追加

追加题目时携带任务 `version`，数据库只允许版本匹配的追加操作成功，并原子更新 `questions_json`、`generated_count` 和 `version`。进度保存独立使用 `progress_version`，避免答题保存和题目追加互相覆盖。

### 4. 首题路由与后续题等待分离

生成页只在快照出现第一道有效题时跳转答题页。答题页以 `current_index` 判断当前题是否可用；不可用时显示等待状态并继续轮询，不把“暂未生成”当成生成失败。任务失败且存在部分题目时保留题目并显示继续生成入口。

### 5. 保留单题质量校验和降级

每道题独立经过结构、题干、知识点和重复校验；失败只影响当前题。重试耗尽时使用与当前主题相关的不同降级模板，或将任务置为可重试失败，禁止用同一泛化题填满整套题。

## Risks / Trade-offs

- [轮询请求增加] → 使用单飞锁、6 秒基准间隔、异常时 8 秒退避和终态停止，避免重复请求和微信请求超时。
- [单题调用次数增加] → 复用一次资料准备结果；只对失败题重试；限制单题超时和最大尝试次数。
- [模型返回顺序或内容不稳定] → 以数据库追加顺序为准，客户端按任务版本和题目 ID 合并，拒绝旧快照回退。
- [进程重启导致后台任务中断] → 任务保留已生成题目和答题记录，启动恢复逻辑将未完成任务标记为可重试，不创建重复题目。
- [降级题质量低于模型题] → 记录单题失败原因和降级标记，优先保留可答性与题目多样性，后续可单独优化降级生成器。

## Migration Plan

1. 保持现有生成任务表字段兼容，继续使用 `questions_json`、`generated_count`、`version` 和 `progress_version`，无需数据迁移。
2. 后端先切换为无蓝图的逐题生成循环，并补充任务与单题测试。
3. 前端更新生成页和答题页的首题跳转、增量合并、等待和恢复逻辑。
4. 在本地、微信开发者工具和真实 API 流程验证后发布。
5. 如需回滚，恢复旧的任务执行器；已完成任务仍可按原题组读取，未完成任务可通过重试接口重新生成。

## Context

领域模型已经定义 `single | multiple | judge`，`selected_answers` 已使用数组；答题页也已有多选切换、互斥选择、集合判题和题型标签。当前实际缺口在生成端：同步和增量 Prompt 允许模型自由选择题型，没有在持久化前验证 4/1/1 配额；判断题仅校验单一答案，没有统一两个判断选项的语义；多选题缺少“可多选”提示。

本变更跨越 LLM 生成、增量任务、前端答题和报告兼容，因此需要统一约束。参见 `proposal.md` 和 `specs/quiz-question-types/spec.md`。

## Goals / Non-Goals

**Goals:**

- 同步和增量生成稳定产出 4 道单选、1 道多选、1 道判断。
- 在题目写入任务或返回 API 前完成题型和答案校验。
- 补齐多选提示、判断题规范、进度恢复和报告回显测试。
- 保持现有 API、数据库和历史题组兼容。

**Non-Goals:**

- 不增加简答题、编程题或语音题。
- 不允许用户自行配置题型数量。
- 不改变题目总数 6、岗位、难度或数据源路由。
- 不引入新的六题蓝图调用，也不增加一次前置模型请求。
- 不修改底部导航、用户系统、知识库或图片生成流程。

## Decisions

### 1. 使用确定性题号配额，不依赖模型自行分配

定义固定目标序列，例如 `single, single, single, single, multiple, judge`。同步生成 Prompt 明确整组配额；增量生成按当前题号把目标类型传入单题 Prompt，并在返回后检查 `question.type`。

题型顺序不属于对外契约，未来可以用同一组配额做确定性轮换，但一次任务内必须先确定且不能随重试变化。

选择该方案的原因：

- 不增加前置模型调用，不增加首题等待时间。
- 模型只负责当前题内容，后端负责可验证的题型约束。
- 单题重试时目标类型不变，不会因失败破坏最终组成。

替代方案是让模型先生成六题蓝图并分配题型。该方案增加延迟，且项目此前已取消蓝图依赖，因此不采用。

### 2. 在 Pydantic 通用校验之外增加题型专用校验

保留现有 `Question` 基础约束，并增加以下规则：

- `single`：恰好一个答案。
- `multiple`：至少两个正确答案。
- `judge`：恰好两个选项、恰好一个答案；标准化后选项文本必须对应“正确”和“错误”。

整组 `Quiz` 再统计类型，完成题组必须满足 4/1/1。增量任务尚未完成时只校验当前题是否符合题号目标，不能提前执行整组校验。

判断题继续沿用普通选项结构和答案 key，不增加布尔字段。这样前端、答案记录、报告和历史数据不需要分支数据模型。

### 3. 同步和增量生成共享题型契约

建立小型题型工具模块或纯函数，提供：

- 6 题目标类型序列；
- 按题号取得目标类型；
- 题型标签和 Prompt 指令；
- 单题目标类型验证；
- 完整题组配额验证。

同步 Prompt、增量 Prompt、降级题目和测试数据使用同一来源，避免多处写死后出现比例漂移。该模块不负责知识点规划，也不生成六题蓝图。

### 4. 模型错误先重试，降级题也必须符合目标类型

模型返回错误类型、无效多选答案或无效判断选项时，视为当前单题失败，进入现有单题重试。重试耗尽后，现有降级题生成器按当前目标类型构造合法题目；若降级题仍未通过题型校验，则任务进入失败状态，不持久化半合法题目。

同步整组生成若配额不正确，使用现有整组重试策略，不在服务端把题型字段强行改写。仅修改 `type` 会导致答案数量、选项语义与题型不一致。

### 5. 前端复用答案数组和现有选择逻辑

多选继续使用选项 key 数组；正确性通过集合大小一致且每个用户答案都在标准答案中判断。判断题和单选题点击时替换整个数组。

前端只新增：

- 多选题题型区域中的“可多选”提示；
- 判断题选项文本的明确展示与必要样式；
- 针对三种题型的纯函数/页面行为测试。

提交后选项保持只读，上一题回看使用已保存答案恢复选中状态，现有 `AnswerRecord`、Zustand Store 和 API 不改字段。

### 6. 不进行数据库迁移

`questions_json` 已包含题型字段，`answer_records_json` 已保存答案数组。历史题组默认均为 `single` 也能继续读取，因此本变更不新增表、不改列、不执行数据回填。

## Risks / Trade-offs

- [固定后两题为多选和判断可能让用户较晚接触新题型] → 题型序列集中定义，后续可在不改变 4/1/1 契约的情况下轮换顺序。
- [模型按要求返回类型但题干仍不适合该题型] → Prompt 明确题型语义，Pydantic 校验答案数量，增加真实模型人工抽检。
- [判断题使用“是/否”等同义词导致校验过严] → Prompt 固定要求“正确/错误”，后端只接受有限同义词并在输出模型中标准化为中文展示文本。
- [同步与增量路径约束不一致] → 共享题型契约函数，并分别增加 API 和 Service 测试。
- [多选答案顺序导致误判] → 使用无序集合语义比较，持久化仍保留数组以兼容 API。

## Migration Plan

1. 先加入共享题型契约和后端测试，不改变 API Schema。
2. 更新同步/增量 Prompt、单题校验和降级题生成。
3. 更新前端提示和三种题型行为测试。
4. 运行后端全量 pytest、前端 typecheck/test/build。
5. 在微信开发者工具生成一组题，验证 4/1/1 组成、三种作答、返回恢复和报告回看。

回滚时恢复 Prompt、配额校验和前端提示即可；数据库没有迁移，已生成的多选和判断题仍符合旧版领域模型，可继续读取。

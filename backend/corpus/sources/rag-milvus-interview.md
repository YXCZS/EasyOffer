# RAG 与 Milvus 技术面试知识

本资料由 EasyOffer 项目整理，用于技术面试检索评估。技术依据包括 Milvus 官方文档、LangChain 官方 RAG 文档与 PyMilvus API 文档。资料版本为 2026-08-v1，使用时应结合生产环境的 Milvus 与 LangChain 具体版本核对 API。

## RAG 基本链路

问题：一个典型 RAG 系统由哪些阶段构成？
答案：离线阶段通常包含来源登记、解析、清洗、结构化切分、Embedding 和索引；在线阶段通常包含查询理解、检索、过滤或重排、上下文组装、生成与证据引用。工程实现必须分别评估检索质量和生成质量，不能只用“向量成功写入”判断系统可用。

问题：为什么面试知识库不应只采用固定字符长度切分？
答案：固定长度可能把问题、答案、边界条件和代码示例拆开，导致召回片段无法支持完整题解。更可靠的策略是先识别问答、标题、列表和代码块等结构，形成父知识单元；只有父单元过长时才递归切成带重叠的子块。命中子块后再按 parent_id 精确恢复父上下文。

问题：父子分块怎样兼顾召回精度和答案完整性？
答案：子块较短，适合生成向量并参与相似度召回；父单元保存完整问题与答案。检索先命中子块，再用 parent_id、document_id 和 document_version 做标量查询恢复父单元。父级恢复必须是精确过滤，不能用文件名再次执行相似度搜索。

## Milvus 数据建模

问题：Milvus 中为什么要使用确定性主键和 auto_id=false？
答案：离线语料管线可能重复执行。使用 document_id、版本、父子序号和内容哈希生成稳定字符串主键，并将 auto_id 关闭，可以通过 upsert 幂等覆盖同一实体，避免每次重跑都新增重复向量。

问题：Milvus 动态字段适合保存哪些知识库元数据？
答案：动态字段适合保存 document_id、corpus_version、parent_id、role_tags、technology、status、source_url、license_status 等用于过滤与追溯的扩展元数据。核心字段命名应稳定，发布检索必须显式过滤 status=published，避免候选内容污染线上结果。

问题：公共知识库为什么需要候选版本而不能导入后直接发布？
答案：新数据可能包含解析错误、重复、来源许可问题或岗位标签污染。候选版本先以 unpublished 状态写入，完成结构检查、检索基准评估和人工审核后再切换为 published；发布冒烟失败时恢复旧版本状态。这是一种适配 Milvus 非业务事务特性的补偿式发布流程。

问题：Milvus 的标量过滤在 RAG 中有什么价值？
答案：向量相似度只衡量语义接近程度，不能替代权限、版本和发布状态约束。标量过滤可以把检索限制在当前用户、指定文档、目标岗位、已发布语料或指定 corpus_version 范围，再对返回结果做本地防御性复核。

## 检索评估

问题：Hit@5、MRR@5 和 NDCG@5 分别衡量什么？
答案：Hit@5 判断前五条是否至少命中一个相关知识单元；MRR@5 关注第一个相关结果出现的位置；NDCG@5 同时考虑多级相关性和排序位置。三者需要结合岗位污染率、重复率、父上下文恢复率、来源可追溯率和 P95 延迟共同判断。

问题：为什么检索指标通过后仍需要人工抽检？
答案：黄金标签可能不完整，自动指标也无法完全判断技术结论是否正确、是否具有面试价值以及版本是否过时。人工抽检应覆盖高分、低分、冲突和边界案例，并把结论关联到具体 query_id、chunk_id 和来源位置。

问题：怎样避免新资料让已有知识领域发生检索退化？
答案：候选版本与当前版本必须使用相同的查询集、Embedding、过滤条件和 Top-K 参数做回归比较。报告应列出指标差值、排名下降、结果来源变化、岗位污染和延迟变化；强制门槛失败时不得切换活动版本。

## Agentic RAG 边界

问题：Agentic RAG 中公共知识库与联网搜索应如何协作？
答案：路由策略先受权限与产品约束限制，再根据证据质量决定工具。普通登录用户可以先检索已发布公共知识库；证据不足、版本过旧或主题变化快时再调用联网搜索。个人知识库专属模式只允许个人 Milvus 与基础模型，游客保持基础模型模式，工具不可越权扩大。

问题：RAG 证据不足时为什么不能强行声称来自知识库？
答案：低相关或缺少答案的片段会造成错误归因。系统应记录检索工具、来源、置信度和降级原因；证据不足时继续检索、联网搜索或明确回退基础模型，不能把模型固有知识伪装成知识库事实。

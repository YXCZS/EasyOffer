# Redis 技术面试知识

本资料由 EasyOffer 根据 Redis 官方文档整理，面向后端技术面试复习。资料版本为 2026-08-v1。技术事实参考 Redis 官方的持久化、复制、集群、数据类型、过期策略、内存诊断和分布式锁文档；实际参数应结合所使用的 Redis 版本与业务数据安全目标确定。

## 持久化

问题：Redis RDB 和 AOF 的核心区别是什么？
答案：RDB 在指定时点生成数据集快照，文件紧凑、适合备份和快速恢复，但故障时可能丢失最近一次快照后的写入。AOF 追加记录写命令，重启时通过重放恢复数据，通常具有更小的数据丢失窗口，但文件和写盘开销更高。Redis 可以同时启用两者：RDB 便于备份与恢复，AOF 提供更强的写入持久性。

问题：Redis 宕机后怎样尽量减少数据丢失？
答案：应先按业务的 RPO 和性能目标选择持久化。AOF 的 appendfsync=always 每次写入都同步磁盘，数据安全更强但吞吐最低；everysec 通常每秒同步一次，官方文档说明灾难时一般最多丢失约一秒写入；no 由操作系统决定刷盘时机。生产上还应结合 RDB 备份、主从复制、故障演练和恢复验证，复制本身不能替代持久化，也不能保证异步复制零丢失。

问题：RDB 快照生成期间 Redis 如何处理写请求？
答案：执行 BGSAVE 时，Redis 主进程 fork 子进程，由子进程把快照写入临时文件，完成后原子替换旧 RDB。父进程继续处理客户端请求。fork 后依赖操作系统的 copy-on-write：未被修改的内存页由父子进程共享，发生写入时才复制相关页。大数据集上的 fork 和写入密集场景会增加延迟与额外内存，必须监控。

问题：AOF 重写为什么不需要停止全部线上写入？
答案：AOF rewrite 在后台生成能够重建当前数据集的最小命令集合，而主进程仍继续接收写请求并追加增量。重写完成后，Redis 合并重写期间的增量并切换到新 AOF 文件。该过程显著压缩历史冗余命令，但 fork、copy-on-write、磁盘带宽和重写缓冲仍可能带来延迟抖动。

## 复制与集群

问题：Redis 主从复制首次同步和断线重连分别怎样处理？
答案：首次复制或无法增量续传时执行 full resynchronization：主节点生成快照发送给副本，并把快照期间的新命令流继续发送。短暂断线后优先使用 replication backlog 与复制偏移量做 partial resynchronization，只补发缺失命令；backlog 已覆盖不到所需偏移时再回退全量同步。Redis 复制默认是异步的，因此主节点故障时不能承诺零数据丢失。

问题：Redis Cluster 为什么使用哈希槽？
答案：Cluster 把键空间划分为 16384 个槽，槽位通常按 CRC16(key) mod 16384 计算，每个主节点负责一组槽。扩缩容时迁移槽即可，不必整体重算所有键。客户端访问错误节点时可能收到 MOVED 或 ASK 重定向。多键操作要求相关键位于同一槽，可用花括号中的 hash tag 让一组键映射到相同槽。

## 缓存与数据结构

问题：缓存雪崩、击穿和穿透分别是什么，如何治理？
答案：雪崩是大量缓存同时失效或缓存服务不可用，导致请求集中访问后端；可使用过期时间随机化、分批预热、限流和高可用。击穿是单个热点键失效后并发回源；可使用互斥重建、逻辑过期或请求合并。穿透是持续查询本不存在的数据；可缓存空结果、做参数校验，并在适合时使用 Bloom Filter。三类问题都需要限流、熔断和降级作为最后保护，不能只依赖一种缓存技巧。

问题：大量 key 同时过期为什么可能造成延迟抖动？
答案：Redis 同时使用惰性过期和主动过期：访问键时检查是否过期，后台也会周期性抽样清理。大量键在同一时刻到期会增加主动清理和缓存回源压力，造成 CPU 与下游负载尖峰。应给过期时间增加随机抖动、分批预热热点数据，并监控过期、命中率和后端流量。

问题：怎样比较 Redis 五种常用数据结构？
答案：String 是二进制安全的字节序列，适合缓存值、计数和位操作；Hash 保存字段和值，适合对象属性；List 按插入顺序保存元素，适合简单队列但复杂消息场景通常优先 Stream；Set 保存不重复成员，适合集合运算；Sorted Set 的成员唯一并按 score 排序，适合排行榜和范围查询。选型应从访问模式、复杂度、内存和原子操作需求出发。

问题：如何用 Redis 实现分布式锁并避免误删除？
答案：单实例基础做法是使用 SET key unique_value NX PX ttl 原子获取锁，value 必须是每个持有者唯一的随机值。释放时用 Lua 脚本原子比较 value 并删除，避免超时后旧持有者误删新持有者的锁。还要处理业务执行超过租期、客户端暂停、故障转移和锁服务可用性；对严格一致性场景，应重新评估 Redis 锁是否满足系统安全模型。

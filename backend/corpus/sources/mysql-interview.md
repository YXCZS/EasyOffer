# MySQL 技术面试知识

本资料由 EasyOffer 根据 MySQL Reference Manual 整理，面向 MySQL 8.4 LTS 与 InnoDB 技术面试复习。资料版本为 2026-08-v1。不同版本的优化器、复制和执行计划字段可能变化，生产结论应以目标版本的官方文档和真实执行计划为准。

## 索引与查询优化

问题：InnoDB B+Tree 索引为什么适合范围查询？
答案：B+Tree 通过有序键值逐层缩小搜索范围，叶子页按键顺序组织，并通过页结构支持连续扫描。定位范围起点后可以沿叶子页顺序读取后续记录，避免对整表逐行比较。树高通常较低，既适合等值查询，也适合前缀明确的范围与排序；实际收益仍取决于选择性、回表成本和读取页数。

问题：InnoDB 聚簇索引和二级索引有什么区别？
答案：InnoDB 的聚簇索引叶子记录保存完整行数据，通常由主键承担；没有合适主键时 InnoDB 会选择或生成内部聚簇键。二级索引叶子记录保存二级索引键和主键值。查询所需列不在二级索引中时，先命中二级索引，再以主键访问聚簇索引取得整行，这一步通常称为回表。

问题：什么是覆盖索引，怎样减少回表？
答案：如果查询需要的过滤、连接或返回列都能从一个索引取得，就可以只扫描该索引而无需再次访问聚簇索引，这称为覆盖索引。可以根据高频查询设计联合索引并避免无意义的 SELECT *，但不能为了覆盖所有列创建过宽索引，因为它会增加存储、缓存占用和写放大。

问题：联合索引的最左前缀原则应怎样理解？
答案：联合 B+Tree 索引按定义顺序组织键。查询条件能从索引最左列开始形成连续可用前缀时，优化器更容易利用其定位和排序。跳过前导列、对索引列做不可索引表达式或某些范围条件之后的列，可能削弱后续列的定位能力。不过 MySQL 8 的优化器可能使用 skip scan、index condition pushdown 等策略，面试回答不能把“某列一定失效”说成绝对规则，应以 EXPLAIN 和实际成本为准。

问题：EXPLAIN 中排查慢查询应重点看什么？
答案：先看访问表的顺序和 access type，再看 possible_keys、实际 key、key_len、rows、filtered 和 Extra，判断是否全表扫描、扫描行数估计过大、出现临时表或额外排序。MySQL 8 可用 EXPLAIN ANALYZE 获取真实执行时间、循环次数和实际行数。执行计划只是入口，还要结合慢日志、数据分布、统计信息、锁等待、I/O、缓存命中和并发负载定位瓶颈。

问题：一条 SQL 很慢应按什么顺序排查？
答案：先确认是稳定慢还是偶发慢，并从慢查询日志取得原始 SQL、耗时和扫描行数；随后使用 EXPLAIN 或 EXPLAIN ANALYZE 检查访问路径、估算偏差和算子耗时。再核对索引、统计信息、数据倾斜、返回行数、排序与临时表，同时检查 performance_schema 中的锁等待、I/O 和资源争用。优化后要用相同数据与负载回归，避免只让单条 SQL 变快却放大写入或其他查询成本。

## 事务、MVCC 与锁

问题：InnoDB 支持哪些事务隔离级别，默认是什么？
答案：InnoDB 支持 READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ 和 SERIALIZABLE 四个标准隔离级别，默认是 REPEATABLE READ。隔离越强不等于所有场景性能越差，但通常会增加并发协调约束。应用需要根据一致性语义、锁冲突和复制方式选择，不能通过隔离级别名称推断所有具体行为。

问题：脏读、不可重复读和幻读分别是什么？
答案：脏读是读到其他事务尚未提交的数据；不可重复读是同一事务两次读取同一行得到不同已提交值；幻读是同一范围查询再次执行时出现或消失满足条件的行。InnoDB 的一致性读通过 MVCC 提供快照视图，锁定读和写操作还会使用记录锁、间隙锁或 next-key 锁。是否出现某种现象取决于隔离级别、读类型和具体语句。

问题：InnoDB 的 MVCC 如何支持可重复读？
答案：InnoDB 为行维护事务相关的隐藏信息，并通过 undo log 保存旧版本。普通一致性读根据 Read View 判断哪个版本对当前事务可见；在 REPEATABLE READ 下，同一事务的多个一致性读通常复用事务快照，因此能看到稳定版本。当前读、加锁读和写操作读取的是符合锁语义的较新版本，不能把所有 SELECT 都简单归为同一种快照行为。

问题：InnoDB 有哪些常见行锁，怎样分析死锁？
答案：常见锁包括记录锁、间隙锁和 next-key 锁；锁定读还涉及共享锁与排他锁。不同事务以不一致顺序获取资源可能形成循环等待，InnoDB 检测到死锁后会回滚其中一个事务。排查时可结合 SHOW ENGINE INNODB STATUS 以及 performance_schema.data_locks、data_lock_waits 查看持有者、等待者、索引和锁模式，并通过统一访问顺序、缩短事务、建立合适索引和重试被回滚事务降低风险。

## 日志与复制

问题：redo log、undo log 和 binlog 各自有什么作用？
答案：redo log 是 InnoDB 的物理重做信息，用于崩溃恢复并支持先写日志再刷新数据页；undo log 保存撤销与历史版本信息，用于事务回滚和 MVCC；binlog 是 MySQL Server 层的逻辑变更日志，服务于复制和时间点恢复。三者层次和用途不同，不能互相替代。

问题：MySQL 两阶段提交解决了什么问题？
答案：当事务同时写 InnoDB redo log 和 Server 层 binlog 时，需要让两份日志对事务提交的判断保持一致。MySQL 通过 prepare 与 commit 协调提交：先让 InnoDB 进入 prepare，再写并持久化 binlog，最后提交存储引擎事务。崩溃恢复时可根据 redo 状态与 binlog 记录判断提交或回滚，避免数据库数据与复制/恢复日志出现相互矛盾的事务结果。

问题：MySQL 复制为什么不能只看“延迟秒数”？
答案：复制源把变更写入 binlog，副本接收并应用事件。延迟可能来自网络、单个大事务、并行度不足、锁等待、I/O 或副本查询负载。排查应同时观察接收与应用位置、线程状态、事务大小、复制错误和系统资源，并确认使用的复制拓扑与一致性要求；异步复制不能天然保证源故障时零数据丢失。

# EasyOffer 20 份 PDF 公共知识库构建全流程

## 1. 文档目的

本文记录 EasyOffer 将 20 份已授权技术面试 PDF 构建为公共 Milvus 知识库的完整工程过程，包括技术选型、数据处理链路、结构化分块、去重、质量门禁、检索评估、发布切换、真实出题验证，以及实施过程中遇到的问题和解决方法。

本文只讨论公共知识库的构建和使用，不讨论 Milvus Standalone 的部署方案。

## 3. 总体处理链路

```text
登记 PDF 来源和授权信息
        ↓
解析 PDF 并保留页码位置
        ↓
清洗控制字符、空白和重复页眉页脚
        ↓
识别问题、答案、章节、列表和代码
        ↓
构建完整父知识单元
        ↓
将过长父单元切成可检索子块
        ↓
精确去重和 SimHash 近似去重
        ↓
生成 text-embedding-v4 向量
        ↓
写入 Milvus unpublished 候选版本
        ↓
执行自动质量检查
        ↓
运行精确父单元检索基准
        ↓
进行人工抽样审查
        ↓
审批并切换为 published
        ↓
通过 Agentic RAG 进行真实出题验证
```

这条链路的核心原则是：资料进入 Milvus 不等于知识库构建成功。只有解析完整、问答边界正确、重复内容受控、检索命中具体知识点、答案能够恢复、来源可追溯，并且真实出题不偏离主题，才能正式发布。

## 4. 来源清单与版本治理

20 份 PDF 统一登记在：

```text
backend/corpus/manifests/full-authorized-v1.yaml
```

每份文档登记以下信息：

- `document_id`：稳定文档标识。
- `path`：本地 PDF 路径。
- `source_name` 和 `source_url`：来源名称和地址。
- `technology`：技术方向。
- `role_tags`：适用岗位。
- `document_version`：文档版本。
- `language`：语言。
- `content_type`：文档类型。
- `license_status`：授权状态。
- `target_corpus_version`：目标语料版本。
- `authority_priority`：重复内容冲突时的来源优先级。

这 20 份 PDF 均经过用户确认授权，因此全部使用：

```yaml
license_status: approved
```

版本化清单使每个知识块都能追溯到原始文档、文档版本、页码和语料版本。以后更新或撤回某份资料时，不需要破坏其他知识数据。

## 5. PDF 解析

PDF 解析使用 `pypdf.PdfReader`，实现位于：

```text
backend/app/corpus/parsers.py
```

解析阶段按页读取文本，并保留：

- `page_start`
- `page_end`
- `start_index`
- `section_path`

解析器会显式识别以下异常：

- PDF 加密：`encrypted_pdf`
- PDF 损坏或不可读：`unreadable_pdf`
- 扫描版或无可提取文本：`scanned_or_empty_pdf`
- 文件不存在：`source_file_not_found`

每份文档独立处理。单个文档失败时会记录失败阶段和原因，不会丢失其他成功文档的统计或阶段产物；但只要候选版本包含失败文档，整个版本就不能通过审批。

## 6. 文本清洗

文本清洗坚持“只修格式，不改结论”。主要处理：

- 将 Windows 和旧式换行统一为 `\n`。
- 删除不可见控制字符。
- 合并连续空格和异常空行。
- 清理行首行尾多余空格。
- 检测乱码标记。
- 删除跨多数页面重复出现的页眉和页脚。

重复页眉页脚的检测方法是统计每页首行和尾行。当同一短文本出现在至少 3 页，并达到约 60% 页面时，将其作为页眉或页脚移除。

没有让大模型改写 PDF 正文，因为改写会破坏证据的可审计性，也可能引入原资料没有的技术结论。

## 7. 结构化父知识单元

固定长度切分容易把问题和答案拆开，因此系统先识别语义边界，再进行长度切分。实现位于：

```text
backend/app/corpus/chunking.py
```

规则识别内容包括：

- `Q1`、`Question 1`、问题编号等明确问题标记。
- 带“什么、如何、为什么、区别、原理、流程、场景”等特征的问句。
- 答案、解析、解答和总结等答案标记。
- Markdown 标题、章节、列表和代码块。
- 跨页延续的答案内容。

系统首先生成父知识单元。父单元尽量保存完整问题和答案，并记录标题、类型、页码、章节、文档哈希、内容哈希和结构置信度。

可选的 DeepSeek 边界分类器只允许返回原文字符区间和类型，不允许重写内容。分类结果必须从字符 0 连续覆盖到正文结尾，不允许重叠或遗漏；模型输出无效时自动回退到确定性规则。本次正式语料构建使用稳定的规则路径，避免为批量解析增加不必要的模型成本和不确定性。

## 8. 父子分块

父单元负责保存完整语义，子块负责向量检索。

```text
父单元：完整问题 + 完整答案 + 来源位置
子块：适合 Embedding 和 Top-K 检索的文本片段
```

过长父单元使用 LangChain `RecursiveCharacterTextSplitter` 切分：

| 参数 | 值 |
|---|---:|
| 子块大小 | 850 字符 |
| 子块重叠 | 100 字符 |
| 父单元建议上限 | 1,800 字符 |
| 单文档最大块数 | 5,000 |

子块通过 `parent_id` 关联父单元。检索命中子块后，系统使用 `parent_id + document_id + document_version + corpus_version` 精确恢复同一父单元的所有子块，并按 `child_index` 排序拼接。

Embedding 文本包含技术、标题、章节和正文，提高向量区分能力；原始证据另存为 `evidence_text`，交给出题模型时不会混入存储层包装信息。

## 9. 稳定 ID 和幂等写入

文档哈希、父单元 ID 和子块 ID 均基于 SHA-256 生成。

子块 ID 综合以下信息：

```text
document_id
document_version
parent_index
child_index
content_hash
```

相同文档版本和相同内容重复运行时会得到相同主键。Milvus 使用 `auto_id=false`，因此重复摄取会覆盖同一实体，而不会不断产生重复数据。

## 10. 精确去重和近似去重

去重实现位于：

```text
backend/app/corpus/dedup.py
```

系统使用两层去重：

1. 精确去重：规范化空白后计算 SHA-256。
2. 近似去重：计算 SimHash，汉明距离不超过 3 时视为近似重复。

去重前先按 `authority_priority` 排序，让专项资料优先于综合资料。Java 热门 200 题属于聚合资料，优先级低于 Java 基础、Java 并发、JVM、MyBatis 等专项 PDF。

最典型的数据是 Java 热门 200 题：

| 指标 | 数量 |
|---|---:|
| 父知识单元 | 193 |
| 识别为重复的子块 | 160 |
| 最终保留子块 | 52 |

这不是丢失 160 道题，而是这些内容已经由更专业的专项 PDF 提供。保留专项版本可以减少重复召回和重复出题。

整个批次去重前共有 1,455 个子块，删除 172 个重复块，最终保留 1,283 个，去重比例约为 11.82%。

## 11. Embedding 与 Milvus 写入

向量化使用阿里云百炼兼容接口：

| 配置 | 值 |
|---|---|
| Embedding 模型 | `text-embedding-v4` |
| 向量维度 | 1,536 |
| Embedding 批大小 | 10 |
| Milvus 相似度 | COSINE |
| 普通检索 Top-K | 5 |

每个 Milvus 实体保存：

- 文档和语料版本。
- 技术方向和岗位标签。
- 父单元 ID 和类型。
- 页码和字符位置。
- 来源名称与地址。
- 授权状态。
- 审核状态和发布状态。
- 原始证据文本。
- 文档、父单元和子块哈希。

首次写入全部使用 `status=unpublished`，因此候选数据不会被小程序的默认公共检索读取。

## 12. 分阶段摄取与恢复

每个文档会保存以下阶段产物：

```text
parsed.json
parents.json
chunks.jsonl
status.json
```

批次级产物包括：

```text
chunks.jsonl
quality.json
report.json
```

稳定的 ingest batch ID 允许重复执行时复用已完成阶段，仅重做缺失或失败阶段。这样大批量 PDF 中某个文档失败时，不需要重新解析其他 19 份成功文档。

最终正式摄取耗时约 159.9 秒，20 份全部成功，0 份失败。

## 13. 自动质量检查

质量检查实现位于：

```text
backend/app/corpus/quality.py
```

检查项包括：

- 空语料或文本过短。
- 乱码。
- 来源缺失。
- 岗位标签缺失。
- 授权未批准。
- 结构置信度过低。
- 问题缺少答案。
- 元数据不完整。
- 同一文档存在多个版本。
- 重复比例异常。

最终结果：

| 检查结果 | 文档数 |
|---|---:|
| 解析成功 | 20 |
| 解析失败 | 0 |
| 存在低结构置信度警告 | 15 |
| 存在重复内容警告 | 10 |
| 阻断级错误 | 0 |

低结构置信度主要来自 PDF 缺少标准标题层级或页面只包含普通段落。它是人工抽样提示，不代表答案缺失。后续父块恢复率和答案完整率均达到 100%，证明这些警告没有造成最终知识缺失。

## 15. 实施过程中遇到的问题

### 15.1 普通技术词被识别为问题

最初过宽的 `Q...` 正则会把 `QPS`、`Queue` 等普通技术词当成问题开头，造成父单元错误切分。

解决方法：只接受明确的 `Q + 编号`、`Question + 编号`、问题编号或具有真实面试问句特征的内容。对于以问号结尾的代码、SQL 占位符、泛型和表达式，也增加排除条件。

### 15.2 连续反问句被切成两个问题

一些题目会先问主问题，再跟一句修辞性追问。原规则看到第二个问号就创建新父单元。

解决方法：如果当前单元还只有问题、尚未出现答案内容，则将紧邻问句保留在同一单元；只有已有答案后出现新问题才切分。

### 15.3 答案跨页后变成孤立段落

PDF 按页提取时，一道题的答案可能从下一页继续。原实现会把下一页识别成新的普通段落。

解决方法：当下一页第一段不是新问题，且页码与上一个父单元连续时，将它合并到上一个父单元，并扩展 `page_end`。

### 15.4 综合资料覆盖专项资料

Java 热门 200 题包含 MyBatis、JVM、并发等多个方向，与专项 PDF 大量重复。若按文档顺序去重，可能保留综合版并删除专项版。

解决方法：增加 `authority_priority`。专项资料优先，综合资料后处理。去重时先按优先级排序，再确定保留项。

### 15.5 跨文档重复被误判为批次质量失败

跨文档重复是整合多套资料时的正常现象，但原质量规则把它与单文档内部异常重复混在一起。

解决方法：分别统计内部重复和跨来源重复。跨来源重复执行去重并记录，不直接阻断发布；只有单文档内部重复比例异常才作为严重问题。

### 15.6 检索评测得到虚假的满分

第一版相关性标签使用 `document_id`。例如查询某个 AI 知识点，只要返回 AI PDF 中任何一段内容都会被判定相关，因此第一次评测曾得到：

| 指标 | 初始结果 |
|---|---:|
| Hit@5 | 100% |
| MRR@5 | 100% |
| NDCG@5 | 约 88.77% |

人工查看发现，查询 Transformer 自注意力时可能返回大模型长短期记忆内容，却仍因来自同一 AI PDF 被判为正确。

解决方法：38 条基准查询全部改为精确 `parent_id` 标注，只有命中对应问题的父知识单元才算相关。

修复后的真实指标为：

| 指标 | 精确父单元评测 |
|---|---:|
| Hit@5 | 100% |
| MRR@5 | 96.93% |
| NDCG@5 | 97.59% |
| 知识覆盖率 | 100% |
| 重复结果率 | 0% |
| 岗位污染率 | 0% |
| 来源追溯率 | 100% |
| 父块恢复率 | 100% |
| 答案完整率 | 100% |
| P50 检索耗时 | 3.643 秒 |
| P95 检索耗时 | 4.168 秒 |

MRR 从 100% 变成 96.93% 不是质量下降，而是评价标准从“同一 PDF 即正确”升级为“具体知识单元正确”。NDCG 则从约 88.77% 提升到 97.59%，说明正确内容的整体排序明显改善。

### 15.7 查询扩展可能导致主题漂移

真实验证“Redis 持久化机制”时，查询扩展曾返回 Redis 数据结构、RDB/AOF、缓存问题等多个方向。如果将第一条扩展结果直接作为唯一检索词，可能召回 Sorted Set 或 List，并导致出题偏离持久化。

同时，原覆盖率计算方式按“命中证据条数 / 主题词数量”计算，曾出现覆盖率 2.5，错误地把偏题证据判为高置信度。

解决方法：

1. 原始主题始终保留在查询计划第一位。
2. 只有完整保留所有主题词的扩展查询才能作为增强查询。
3. 在多个合格查询中选择最短的一个，减少无关上下文。
4. 覆盖率改为“被证据覆盖的主题词数 / 主题词总数”，结果限制在 0 到 1。
5. 检索后只保留主题词覆盖度最高的证据。
6. 出题 Prompt 将用户原始主题设置为硬边界，禁止使用仅属于同一大技术方向的旁支证据。

backend/corpus/benchmarks/full-authorized-v1.yaml

自动门禁通过后，还对以下类型进行人工抽样：

- 高分样本。
- 低分样本。
- 跨页和长答案边界样本。
- 综合来源与专项来源冲突样本。

人工审查记录位于：

```text
backend/corpus/reviews/full-authorized-v1.yaml
```

抽样中发现 MyBatis `#{}` 与 `${}` 查询的综合题库结果比专项结果高约 0.0034。两条内容都正确，专项内容仍位于第二，因此没有阻断发布，但记录为后续重排优化信号。

## 17. 审批和发布

候选版本必须同时满足：

- 没有失败文档。
- 没有阻断级质量问题。
- 检索评估门禁通过。
- 存在版本化人工审查记录。
- 审核人、时间、结论和理由完整。

发布采用补偿式两阶段切换：

1. 将候选版本设置为 `published`。
2. 将旧版本设置为 `inactive`。
3. 执行发布后冒烟检索。
4. 冒烟成功后更新 active version。
5. 任意步骤失败时，将候选恢复为 `unpublished`，旧版本恢复为 `published`，并生成 rollback 报告。

最终状态：

```text
full-authorized-v1: 1,283 published
pilot-official-v1: 38 inactive
```

## 18. Agentic RAG 真实出题验证

发布完成后，不能只验证 Milvus 中存在实体，还要验证实际出题链路能够使用这些知识。

以“Redis 持久化机制”为例，UTF-8 真实调用结果为：

```text
原始主题：Redis 持久化机制
路由：public_kb
工具：public_milvus_search
查询计划：
  1. Redis 持久化机制
  2. Redis 持久化机制 RDB AOF 原理 区别 面试
  3. Redis RDB 持久化 配置 触发条件 优缺点
Milvus 候选：5 条
相关性过滤后：1 条
主题覆盖率：1.0
```

生成的第一题考察：AOF 使用 `everysec` 策略时，实例意外宕机可能丢失最近约一秒的数据。

真实耗时：

| 阶段 | 耗时 |
|---|---:|
| 主题判断、查询扩展、检索和证据过滤 | 约 24.7 秒 |

## 20. 面试角度的经验总结

### 为什么采用父子分块

小块有利于提高向量检索精度，但会破坏答案完整性；大块保留语义，却容易降低召回精度并增加 Token。父子分块让子块负责召回、父块负责提供完整上下文，同时解决二者的矛盾。

### 为什么需要确定性 ID

稳定 ID 支持幂等摄取、断点恢复、精确父块恢复、版本比较和问题追踪。如果使用随机 ID，重复导入、回滚和检索评测都会更难控制。

### 为什么去重不能只看文本相等

多个题库可能使用略有差异的表述讲同一问题。精确哈希只能处理完全相同文本，因此还需要 SimHash 处理近似重复，并通过来源优先级决定保留专项资料还是综合资料。

### 为什么必须建立黄金检索集

仅凭“能搜索到内容”无法证明 RAG 正确。必须预先定义问题对应的具体父知识单元，再计算 Hit、MRR、NDCG、完整性和污染率。相关性标签过粗会制造虚假的高分。

### 为什么检索后还需要过滤

向量相似度反映语义接近，不等于满足用户的精确意图。同属 Redis 的持久化、List 和 Sorted Set 都可能有较高相似度。需要根据用户主题词覆盖率进行后处理，避免旁支证据干扰生成模型。

### 为什么发布必须有候选状态

直接写入线上可检索状态会让未评估内容立刻影响用户。`unpublished → approved → published` 的状态流可以先完成质量检查和检索验证，再原子式切换版本；失败时还可以恢复旧版本。
